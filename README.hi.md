# Capability Value Test｜नई क्षमता के मूल्य का सत्यापन

[English](README.md)｜[简体中文](README.zh-CN.md)｜[繁體中文](README.zh-TW.md)｜[日本語](README.ja.md)｜[한국어](README.ko.md)｜[Русский](README.ru.md)｜**हिन्दी**｜[Español](README.es.md)｜[Français](README.fr.md)｜[Deutsch](README.de.md)｜[Português](README.pt.md)｜[العربية](README.ar.md)

> नई क्षमता के उपयोग को दिखाई देने योग्य और उसके मूल्य को मापने योग्य बनाइए।

Capability Value Test AI Agent के लिए एक सामान्य Skill है। यह जाँचता है कि नई जोड़ी गई क्षमता (जैसे Skill, मॉडल, प्लगइन, MCP Server, ब्राउज़र, ओपन-सोर्स घटक या Agent workflow) वास्तव में इस्तेमाल हुई या नहीं, और क्या उसने पुरानी विधि की तुलना में मापने योग्य मूल्य पैदा किया।

यह पुरानी कार्य-विधि और नई क्षमता जोड़ने के बाद की कार्य-विधि के बीच निष्पक्ष A/B Test बनाता है। डिफ़ॉल्ट रूप से उपयोगकर्ता के नियमित काम या उसके दिए उदाहरणों से तीन प्रतिनिधि कार्य चुने जाते हैं। प्रयोग चलाने से पहले मनुष्य पूरा डिज़ाइन देखता और स्वीकृत करता है। अंत में एक स्वतंत्र, दृश्य और पता लगाने योग्य HTML रिपोर्ट बनती है।

## यह किन प्रश्नों का उत्तर देता है

1. **क्या नई क्षमता वास्तव में इस्तेमाल हुई? इसका प्रमाण कहाँ है?**
2. **क्या उसने मूल्य पैदा किया? क्या उसे मापा जा सकता है?**
3. **क्या उपयोग की प्रक्रिया और वास्तविक मूल्य को दृश्य रूप में समझा जा सकता है?**

## प्रक्रिया

1. नई क्षमता और उसे जोड़ने से पहले तथा बाद की दोनों विधियाँ तय करें।
2. उपयोगकर्ता के नियमित काम से तीन प्रतिनिधि कार्य चुनें।
3. हर दौर में इनपुट, आउटपुट की शर्तें, रोकने का नियम और मूल्यांकन मानदंड समान रखें।
4. पूरा प्रयोग डिज़ाइन मनुष्य को दिखाएँ; अस्वीकृत होने पर सुधार कर फिर प्रस्तुत करें।
5. स्पष्ट स्वीकृति के बाद दोनों विधियों को तीन दौर में चलाएँ और परिणाम, मेट्रिक्स तथा उपयोग के प्रमाण दर्ज करें।
6. अंतर का विश्लेषण करके HTML रिपोर्ट बनाएँ।

उद्देश्य नई क्षमता को जिताना नहीं, बल्कि यह पता लगाना है कि क्या बदला और क्या उपलब्ध प्रमाण उसे अपनाने का समर्थन करते हैं।

## HTML रिपोर्ट

1. **निर्णय सारांश**: सबसे पहले दोनों विधियाँ, निष्कर्ष, मुख्य कारण, मूल्य प्रश्न और परीक्षण तिथि दिखाता है।
2. **मुख्य तुलना और विश्लेषण**: तीन दौर का समेकित डेटा, हर दौर के परिणाम, अवलोकन, बाहरी स्रोत, लाभ, सीमाएँ, ठोस उपयोग-परिस्थितियाँ और अनिश्चितता दिखाता है।
3. **प्रयोग डिज़ाइन और प्रमाण**: कार्य चयन, निष्पक्ष शर्तें और निर्णय मानदंड समझाता है। हर दौर खोलने पर दो timelines दिखती हैं; model/tool calls और raw logs उसी चरण से जुड़े होते हैं जहाँ वे हुए।

उपलब्ध न होने वाले मेट्रिक्स को शून्य नहीं, “उपलब्ध नहीं” दिखाया जाता है। संवेदनशील जानकारी हटाना आवश्यक है।

## रिपोर्ट स्वयं बनाएँ

```bash
python3 scripts/render_report.py tests/sample-experiment.json --output report.html
```

Renderer केवल Python standard library का उपयोग करता है और offline खुलने वाली एक HTML file बनाता है।

नवीनतम संस्करण एक versioned और fixed report format का उपयोग करता है। हर report में वही sections और वही क्रम रहता है, और प्रत्येक मुख्य heading के नीचे उसका अर्थ समझाने वाला text होता है। Default भाषा उपयोगकर्ता की बातचीत की भाषा होती है और ऊपर दाईं ओर से बदली जा सकती है। Analysis में प्रयोग के परिणाम, स्रोतों पर आधारित बाहरी research और अंतिम recommendation अलग-अलग दिखते हैं, तथा उपयोग के scenarios को व्यक्ति, task और environment के रूप में स्पष्ट किया जाता है।

## सीमाएँ

- तीन प्रतिनिधि कार्य एक run की संयोगजन्य समस्या कम करते हैं, लेकिन प्रमाण उन्हीं कार्यों तक सीमित रहता है।
- हर दौर में दोनों विधियों को समान input और समान मानदंड उपयोग करने चाहिए।
- Token और लागत तभी तुलना योग्य हैं जब host उन्हें उपलब्ध कराए।
- उपयोग सत्यापित न हो सके तो निष्कर्ष “प्रमाण अपर्याप्त” होना चाहिए।
- Headless execution को execution record की तरह दिखाया जाता है, live recording की तरह नहीं।
