# Capability Value Test｜新能力价值验证

> 让新能力的使用过程可以被看见，让新能力创造的价值可以被衡量。

Capability Value Test 是一个面向 AI Agent 的通用 Skill，用于验证一项新接入能力（如 Skill、模型、插件、MCP Server、浏览器、开源组件或 Agent 工作流）是否真正被调用，以及它相较于原有方法是否创造了可以被衡量的价值。

它会围绕两种做事方法设计一场公平的 A/B Test：对照组使用原来的做事方法，实验组使用接入新能力后的做事方法。

实验默认包含三轮。三轮任务会优先从用户平时经常完成的任务、常用场景或用户直接提供的案例中选择。每轮实验使用一个具有代表性的任务样本，两种方法处理相同输入，并遵守相同的完成要求和判断标准。

实验方案需要先交给人类审核，只有在人类确认后才会执行。实验结束后，它会生成一份独立、可视化、可追溯的 HTML 报告，帮助人类判断：这项能力是否真的被调用，以及它是否值得采用。

报告默认使用用户与 Agent 对话时的主要语言，并支持通过右上角的下拉菜单切换其他语言。报告中的解释、分析和建议会随语言切换，原始命令、日志和调用证据保持原文，避免翻译破坏证据。

## 为什么需要它

在 AI 时代，我们会不断为 Agent 接入新的模型、Skill、插件、MCP Server、开源组件和工作流。但是，“成功接入”并不等于“产生价值”。人类通常无法直接回答：

1. **它真的被调用了吗？证据在哪里？**
2. **它真的带来价值了吗？具体带来了什么价值，能否量化？**
3. **能否通过可视化的方式，直观感受到新能力的使用过程和具体价值？**

Capability Value Test 要解决的，就是新能力接入以后，**使用过程无法被可视化感知、实际价值无法被量化判断**的问题。

它的目标不是证明新能力一定更好，而是通过真实对照实验回答：接入新能力后的做事方法，相较于原来的方法发生了什么变化，这些变化是否足以支持采用它？

## 它如何工作

1. 明确要验证的新能力，以及接入前后的两种做事方法。
2. 根据用户平时经常完成的任务、过往对话中出现的常用场景，或者用户直接提供的案例，选择三个具有代表性的任务样本。
3. 每轮实验都让原方法和新方法处理相同输入，并遵守相同的输出要求、停止条件和判断标准。
4. 明确结果应该如何判断，包括信息是否正确、是否完整，以及任务耗时从什么时候开始和结束。
5. 把完整实验方案交给人类审核；如果没有通过，就根据反馈修改并重新提交。
6. 获得批准后，分别执行三轮原方法和新方法。
7. 记录每轮实验的执行过程、结果、耗时、可用指标和调用证据。
8. 整理实验直接观察到的内容。如果实验无法完整说明新能力的优劣势和适用场景，再检索官方文档、官方仓库或其他可靠资料作为补充。
9. 将三轮实验数据、实验观察、外部资料和综合判断写入固定格式的 HTML 报告。

## HTML 报告会展示什么

### 顶部决策摘要

报告顶部会直接展示：

- 原方法与新方法分别是什么；
- 最终建议是采用、暂不采用，还是证据不足；
- 得出这一结论的主要原因；
- 本次实验测试了什么；
- 希望回答的价值问题；
- 实验日期。

顶部不设置编号，让用户打开报告后先看到最重要的结论。

### 一、核心对比与实验分析

这一部分会展示：

- 结果质量；
- 任务完成耗时；
- Token 使用量；
- 调用成本；
- 三轮实验的总体数据；
- 原方法和新方法分别取得了什么结果；
- 三轮实验各自的任务、结果和主要差异；
- 实验直接观察到的内容；
- 外部资料及其真实来源链接；
- 新能力的优势和劣势；
- 适合使用和不适合使用的具体场景；
- 实际使用建议；
- 当前结论仍然存在的不确定性。

每个核心指标都会同时显示原方法和新方法的数据，并用一行文字说明新方法相较于原方法提高或降低了多少。宿主没有提供的数据会显示为“不可用”，不会被当作零。

### 二、实验设计与证据

这一部分会说明为什么选择这三个任务、这些任务与用户日常工作的关系、两种方法如何保持相同的对比条件，以及结果质量和任务完成情况如何判断。

每轮实验都可以单独展开。展开后，报告会左右并列展示原方法和新方法的执行时间线。时间线从任务开始时的 `00:00` 计算，只展示真实记录到的关键动作。

模型调用、工具调用、命令、输入输出、错误和原始日志会附在实际发生的时间节点中。用户可以点击对应节点查看证据，不需要在报告底部寻找一整段日志。

时间线是根据真实执行记录生成的，不是实时录屏。没有被记录到的过程会显示为“不可用”，不会被补写或推测。

### 多语言报告

报告默认使用用户与 Agent 对话时的主要语言。右上角提供语言切换按钮，点击后可以通过下拉菜单切换其他语言。

报告中的标题、解释、实验分析和使用建议会随语言切换。原始命令、模型调用、工具调用、错误信息和执行日志保持原文，避免翻译改变证据内容。

## 人类审批是必需步骤

```text
原来的做事方法 + 接入新能力后的做事方法
                    ↓
      从用户常做的任务中选择三个样本
                    ↓
              设计三轮实验
                    ↓
          人类审阅 ── 不通过 → 修改后重新审阅
                    ↓ 通过
          分别执行三轮原方法和新方法
                    ↓
       实验结果 + 调用证据 + 外部资料
                    ↓
        固定格式的可视化 HTML 报告
                    ↓
                 最终建议
```

批准只对当次展示的确切方案有效。登录、付费、提交、发消息、删除等有后果的动作，仍需遵守各自的授权规则。

## 公平实验原则

每轮实验中，原方法和新方法应处理相同的任务样本、使用相同输入、遵守相同限制，并采用相同的输出要求、停止条件、计时范围和质量标准。

三轮实验不应只是重复运行完全相同的输入。三个样本应来自用户真实、常见且具有代表性的任务，用于观察新能力在不同任务中的稳定表现、具体优势和能力限制。

如果不知道用户平时会完成什么任务，应先向用户了解，或者把拟定任务明确标注为假设，不能直接使用与用户无关的专业测试。

无法完全一致时，报告必须说明差异及其可能造成的影响。

## 适用场景

它可以验证新接入的 Skill、模型、插件、MCP Server、浏览器或自动化引擎、开源组件、数据处理能力、Agent 工作流及原有流程的新版本。

例如：

- Chrome 与 Lightpanda 完成相同网页任务，哪一种方法更高效？
- 两个模型完成相同分析任务，质量、耗时和 Token 消耗有什么差异？
- 安装新 Skill 后，是否减少了操作步骤和任务完成耗时？
- 接入 MCP Server 后，是否比原有 API 或人工流程更高效？

实验结束后，报告不会直接把三轮测试结果推广到全部场景，而是结合实验结果与可靠资料，说明结论适用于哪些具体人物、任务和环境，以及哪些场景仍然需要补充测试。

## 使用方式

```text
请使用 Capability Value Test，验证接入 Lightpanda 后的新方法，相较于原来的浏览器操作方法是否带来了价值。
```

或者：

```text
请对比接入这个新模型前后的两种做事方法，重点比较结果质量、任务完成耗时和 Token 使用量。先把实验方案交给我确认，不要直接执行。
```

Agent 应先提交实验方案，等待人类批准后再运行。

## 手动生成报告

渲染器只依赖 Python 标准库：

```bash
python3 scripts/render_report.py tests/sample-experiment.json --output report.html
```

报告是独立、自包含的 HTML 文件，可以直接在现代浏览器中打开，不需要部署网站或连接外部服务。示例文件只是演示数据，不代表任何真实产品的测试结论。

HTML 使用带版本号的固定报告格式。每份报告保持相同的板块和顺序，并在每个主要标题下保留简短解释，帮助用户理解这个板块展示什么、证据应该如何阅读。不同实验只替换 `experiment.json` 中的内容，不为单次实验重新设计版式。

## 项目边界

- 默认执行三轮具有代表性的任务。三轮实验能够减少单次偶然性，但仍然只能提供当前任务范围内的方向性证据。
- 三轮任务应基于用户常做的任务、常用场景或用户直接提供的案例。
- 公平对照要求两种方法在每轮中处理相同输入，并采用相同要求和判断标准。
- Token 和成本是否可用，取决于宿主是否提供。
- 无法验证新能力确实被调用时，结论必须是“证据不足，需要补充实验”。
- 无头能力不一定有实时可视化界面，报告会展示带时间节点的真实执行记录和调用证据，不会将重建的时间线冒充实时录屏。
- 三轮实验不能代替正式的统计研究，也不能证明新能力在所有任务中都更好。

## 项目愿景

我们希望，人类不必只依赖一句“已经接入成功了”，而是能够直接看到新能力是否真的被调用、如何运行、与原有方法有什么差异、创造了多少价值、适合哪些场景，以及是否应该采用。

**让新能力的使用过程可以被看见，让新能力创造的价值可以被衡量。**
