> 让新能力的使用过程可以被看见，让新能力创造的价值可以被衡量。

Capability Value Test 是一个面向 AI Agent 的通用 Skill，用于验证一项新接入能力（如 Skill、模型、插件、MCP Server、浏览器、开源组件或 Agent 工作流）是否真正被调用，以及它相较于原有方法是否创造了可以被衡量的价值。

它会围绕两种做事方法设计一场公平的 A/B Test：对照组使用原来的做事方法，实验组使用接入新能力后的做事方法。实验方案需要先交给人类审核，只有在人类确认后才会执行。

实验结束后，它会生成一份独立、可视化、可追溯的 HTML 报告，帮助人类判断：这项能力是否真的被调用，以及它是否值得采用。

## 为什么需要它

在 AI 时代，我们会不断为 Agent 接入新的模型、Skill、插件、MCP Server、开源组件和工作流。但是，“成功接入”并不等于“产生价值”。人类通常无法直接回答：

1. **它真的被调用了吗？证据在哪里？**
2. **它真的带来价值了吗？具体带来了什么价值，能否量化？**
3. **能否通过可视化的方式，直观感受到新能力的使用过程和具体价值？**

Capability Value Test 要解决的，就是新能力接入以后，**使用过程无法被可视化感知、实际价值无法被量化判断**的问题。

## 它如何工作

1. 明确要验证的新能力，以及接入前后的两种做事方法。
2. 选择一项两种方法都能完成的真实任务。
3. 统一输入、环境、限制条件和评价标准，设计公平的 A/B Test。
4. 把完整实验方案交给人类审核；不通过就根据反馈修改并重新提交。
5. 获得批准后，分别执行对照组和实验组。
6. 记录两组的执行过程、结果、指标和调用证据。
7. 分析新能力带来的实际变化并生成独立 HTML 报告。

目标不是证明新能力一定更好，而是回答：接入新能力后的做事方法相较于原来的方法发生了什么变化，这些变化是否足以支持采用它？

## HTML 报告会展示什么

### 1. 最终建议

报告会给出三种结论之一：

- **建议采用**
- **暂不采用**
- **证据不足，需要补充实验**

报告还会解释结论依据、新能力的优势与问题、适用和不适用的场景，以及当前实验的限制。

### 2. 价值表现与收益

报告会对比结果质量、任务完成耗时、Token 使用量、调用成本、操作步骤以及错误与重试情况。它不仅展示数字，还会解释耗时或 Token 减少了多少、质量是否变化、效率提升是否伴随损失，以及新能力在哪些场景更有价值。

不同实验可以根据目标选择指标；宿主没有提供的数据会显示为“不可用”，不会被伪装成零。

### 3. 能力调用证明

HTML 报告最底部会分别保留两组的执行证据，例如：

- 实际执行的命令
- 工具或接口调用记录
- 关键输入和输出
- 执行日志与时间戳
- 任务 ID 和返回状态
- 错误与重试记录

这些证据用来验证实验是否真的调用了目标能力，而不是只依赖 Agent 的文字说明。敏感信息必须先脱敏；API Key、访问令牌、Cookie 和无关个人数据不得进入报告。

## 人类审批是必需步骤

```text
原来的做事方法 + 接入新能力后的做事方法
                    ↓
                 设计实验
                    ↓
          人类审阅 ── 不通过 → 修改后重新审阅
                    ↓ 通过
              分别执行两种方法
                    ↓
        可视化 HTML 报告 + 最终建议
```

批准只对当次展示的确切方案有效。登录、付费、提交、发消息、删除等有后果的动作，仍需遵守各自的授权规则。

## 公平实验原则

两组应尽可能完成相同任务、使用相同输入、遵守相同限制、采用相同计时范围和质量标准，并保留同等级的执行证据。无法完全一致时，报告必须说明差异及其可能造成的影响。

## 适用场景

它可以验证新接入的 Skill、模型、插件、MCP Server、浏览器或自动化引擎、开源组件、数据处理能力、Agent 工作流及原有流程的新版本。

例如：

- Chrome 与 Lightpanda 完成相同网页任务，哪一种方法更高效？
- 两个模型完成相同分析任务，质量、耗时和 Token 消耗有什么差异？
- 安装新 Skill 后，是否减少了操作步骤和任务完成耗时？
- 接入 MCP Server 后，是否比原有 API 或人工流程更高效？

## 使用方式

```text
请使用 Capability Value Test，验证接入 Lightpanda 后的新方法，相较于原来的浏览器操作方法是否带来了价值。
```

或者：

```text
请对比接入这个新模型前后的两种做事方法，重点比较结果质量、任务完成耗时和 Token 使用量。先把实验方案交给我确认，不要直接执行。
```

Agent 应先提交实验方案，等待人类批准后再运行。

## 手动生成报告

渲染器只依赖 Python 标准库：

```bash
python3 scripts/render_report.py tests/sample-experiment.json --output report.html
```

报告是独立、自包含的 HTML 文件，可以直接在现代浏览器中打开，不需要部署网站或连接外部服务。示例文件只是演示数据，不代表任何真实产品的测试结论。

## 项目边界

- 每组一次运行只能提供方向性证据，不能代替统计结论。
- 公平对照要求两种方法能够完成相同的代表性任务。
- Token 和成本是否可用，取决于宿主是否提供。
- 无法验证新能力确实被调用时，结论必须是“证据不足，需要补充实验”。
- 无头能力不一定有实时可视化界面，报告会展示真实事件和输出记录，不会将重建的时间线冒充实时录屏。
