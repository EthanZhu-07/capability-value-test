# Capability Value Test｜新能力价值验证

> 让新能力的使用过程可以被看见，让新能力创造的价值可以被衡量。

Capability Value Test 是一个面向 AI Agent 的通用 Skill，用于验证一项新接入能力（如 Skill、模型、插件、MCP Server、浏览器、开源组件或 Agent 工作流）是否真正被调用，以及它相较于原有方法是否创造了可以被衡量的价值。

它会围绕两种做事方法设计一场公平的 A/B Test：对照组使用原来的做事方法，实验组使用接入新能力后的做事方法。实验任务会结合用户的知识背景进行设计，减少不必要的专业术语，优先选择用户能够直接理解并自行判断结果是否正确的任务。

实验方案需要先交给人类审核，只有在人类确认后才会执行。实验结束后，它会生成一份独立、可视化、可追溯的 HTML 报告，帮助人类判断：这项能力是否真的被调用，以及它是否值得采用。

报告默认使用用户与 Agent 对话时的主要语言，并支持通过右上角的下拉菜单切换其他语言。报告中的解释、分析和建议会随语言切换，原始命令、日志和调用证据保持原文，避免翻译破坏证据。

## 为什么需要它

在 AI 时代，我们会不断为 Agent 接入新的模型、Skill、插件、MCP Server、开源组件和工作流。但是，“成功接入”并不等于“产生价值”。人类通常无法直接回答：

1. **它真的被调用了吗？证据在哪里？**
2. **它真的带来价值了吗？具体带来了什么价值，能否量化？**
3. **能否通过可视化的方式，直观感受到新能力的使用过程和具体价值？**

Capability Value Test 要解决的，就是新能力接入以后，**使用过程无法被可视化感知、实际价值无法被量化判断**的问题。

它的目标不是证明新能力一定更好，而是通过真实对照实验回答：接入新能力后的做事方法，相较于原来的方法发生了什么变化，这些变化是否足以支持采用它？

## 它如何工作

1. 明确要验证的新能力，以及接入前后的两种做事方法。
2. 结合用户的知识背景，选择一项两种方法都能完成、用户也能够理解和判断结果的真实任务。对于不影响实验目标的专业术语，应主动删除或改写。
3. 统一两组的输入、环境、限制条件、停止规则和评价标准，设计公平的 A/B Test。
4. 把完整实验方案交给人类审核；如果没有通过，就根据反馈修改并重新提交。
5. 获得批准后，分别执行对照组和实验组。
6. 记录两组的执行过程、结果、指标和调用证据。
7. 首先整理本次实验直接证明了什么。如果单次实验不足以判断这项能力通常适合什么场景、有哪些优势和代价，再检索官方文档、官方仓库或其他可靠的一手资料作为补充。
8. 将实验发现、外部资料和综合判断分开呈现，在不掩盖两者差异的前提下形成最终建议。
9. 使用固定格式生成独立 HTML 报告，并在交付前检查语言、数据、证据、解释字段和板块顺序。

## HTML 报告会展示什么

### 1. 最终建议

报告会给出三种结论之一：

- **建议采用**
- **暂不采用**
- **证据不足，需要补充实验**

报告不仅会给出结论，还会解释：

- 结论由哪些实验结果和外部资料支持；
- 新能力带来了什么具体收益；
- 它存在哪些问题、代价或能力损失；
- 本次实验没有证明什么；
- 下一步应该采用、保留原方法，还是补充实验。

适用场景不会只写成“适合静态页面”“适合自动化”这样的抽象标签。每个场景都需要说明：谁在使用、正在完成什么任务、处于什么环境、为什么适合或不适合、判断依据是什么，以及当前结论的可信程度。

### 2. 价值表现与收益

报告会对比：

- 结果质量；
- 任务完成耗时；
- Token 使用量；
- 调用成本；
- 操作步骤；
- 错误与重试情况。

它不会只展示数字，还会解释：

- 耗时或 Token 减少了多少；
- 结果质量是否发生变化；
- 效率提升是否伴随能力损失；
- 新能力的收益是否足以支持采用。

不同实验可以根据目标选择指标；宿主没有提供的数据会显示为“不可用”，不会被伪装成零。

### 3. 实验发现、外部资料与综合分析

报告会明确区分三层信息：

1. **实验发现**：本次经过用户批准的 A/B Test 直接观察到了什么。
2. **外部资料**：官方文档、官方仓库或其他可靠来源能够支持什么判断。
3. **综合分析**：结合两部分证据后，最终得出了什么建议。

外部资料用于补充单次实验无法回答的背景问题，但不能覆盖、掩盖或为实验失败进行辩解。

例如，官方资料可能说明一项能力适合大规模网页自动化，但如果它在本次实验中没有完成任务，报告必须同时保留这两个事实，而不能利用官方介绍把失败结果包装成成功。

### 4. 能力调用证明

HTML 报告最底部会分别保留两组的执行证据，例如：

- 实际执行的命令
- 工具或接口调用记录
- 关键输入和输出
- 执行日志与时间戳
- 任务 ID 和返回状态
- 错误与重试记录

这些证据用来验证实验是否真的调用了目标能力，而不是只依赖 Agent 的文字说明。敏感信息必须先脱敏；API Key、访问令牌、Cookie 和无关个人数据不得进入报告。

### 5. 固定且可解释的报告格式

所有实验报告使用相同的 HTML 版式和板块顺序。不同实验只替换实验数据，不会为单次任务重新设计一套报告结构。

每个主要板块的标题下方都会保留一段解释文字，帮助用户理解：

- 这个板块展示什么；
- 其中的数据应该如何阅读；
- 哪些内容来自实验；
- 哪些内容来自外部资料；
- 哪些内容属于综合判断；
- 最后一部分证据能够验证什么。

如果报告缺少固定板块、解释字段、格式版本，或者板块顺序发生变化，渲染器会拒绝生成报告，而不是交付一份结构不完整的 HTML。

报告默认使用用户的对话语言。右上角提供语言切换按钮，点击后展开下拉菜单。切换语言时，整份报告的说明性内容同步变化；原始命令、日志、错误信息和工具输出保持不变。

## 人类审批是必需步骤

```text
原来的做事方法 + 接入新能力后的做事方法
                    ↓
            设计一项容易理解的实验
                    ↓
          人类审阅 ── 不通过 → 修改后重新审阅
                    ↓ 通过
              分别执行两种方法
                    ↓
          实验结果 + 外部资料补充
                    ↓
        固定格式的可视化 HTML 报告
                    ↓
                 最终建议
```

批准只对当次展示的确切方案有效。登录、付费、提交、发消息、删除等有后果的动作，仍需遵守各自的授权规则。

## 公平实验原则

两组应尽可能完成相同任务、使用相同输入、遵守相同限制、采用相同停止条件、计时范围和质量标准，并保留同等级的执行证据。

实验任务还应尽量让用户能够直接理解，并能够独立判断结果是否满足要求。如果任务依赖用户并不具备的专业知识，应在提交实验方案前替换为更容易理解、但仍具有代表性的任务。

无法完全一致时，报告必须说明差异及其可能造成的影响。

## 适用场景

它可以验证新接入的 Skill、模型、插件、MCP Server、浏览器或自动化引擎、开源组件、数据处理能力、Agent 工作流及原有流程的新版本。

例如：

- Chrome 与 Lightpanda 完成相同网页任务，哪一种方法更高效？
- 两个模型完成相同分析任务，质量、耗时和 Token 消耗有什么差异？
- 安装新 Skill 后，是否减少了操作步骤和任务完成耗时？
- 接入 MCP Server 后，是否比原有 API 或人工流程更高效？

实验结束后，报告不会直接把一次测试结果推广到全部场景，而是结合实验结果与可靠资料，说明结论适用于哪些具体人物、任务和环境，以及哪些场景仍然需要补充测试。

## 使用方式

```text
请使用 Capability Value Test，验证接入 Lightpanda 后的新方法，相较于原来的浏览器操作方法是否带来了价值。
```

或者：

```text
请对比接入这个新模型前后的两种做事方法，重点比较结果质量、任务完成耗时和 Token 使用量。先把实验方案交给我确认，不要直接执行。
```

Agent 应先提交实验方案，等待人类批准后再运行。

## 手动生成报告

渲染器只依赖 Python 标准库：

```bash
python3 scripts/render_report.py tests/sample-experiment.json --output report.html
```

报告是独立、自包含的 HTML 文件，可以直接在现代浏览器中打开，不需要部署网站或连接外部服务。示例文件只是演示数据，不代表任何真实产品的测试结论。

HTML 使用带版本号的固定报告格式。每份报告保持相同的板块和顺序，并在每个主要标题下保留简短解释，帮助用户理解这个板块展示什么、证据应该如何阅读。不同实验只替换 `experiment.json` 中的内容，不为单次实验重新设计版式。

## 项目边界

- 每组一次运行只能提供方向性证据，不能代替统计结论。
- 公平对照要求两种方法能够完成相同的代表性任务。
- Token 和成本是否可用，取决于宿主是否提供。
- 无法验证新能力确实被调用时，结论必须是“证据不足，需要补充实验”。
- 无头能力不一定有实时可视化界面，报告会展示真实事件和输出记录，不会将重建的时间线冒充实时录屏。

## 项目愿景

我们希望，人类不必只依赖一句“已经接入成功了”，而是能够直接看到新能力是否真的被调用、如何运行、与原有方法有什么差异、创造了多少价值、适合哪些场景，以及是否应该采用。

**让新能力的使用过程可以被看见，让新能力创造的价值可以被衡量。**
